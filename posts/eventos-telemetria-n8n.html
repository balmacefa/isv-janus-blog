Generar eventos de telemetría E2E al sink n8n

Para humanos

Un lab de identidad se ve pobre con el historial vacío. Para que los dashboards y los

workflows de respuesta tengan de qué alimentarse, montamos un **generador de eventos

E2E** que no inventa datos: autentica contra el tenant real de IBM Verify, extrae

usuarios y grupos reales vía SCIM y dispara eventos de telemetría (login, MFA,

SCIM, sesión, riesgo, governance) a un webhook de n8n que los persiste.

El flujo de punta a punta:

  1. Token OAuth2 — POST /v1.0/endpoint/default/token con grant_type=client_credentials

usando el API client del tenant (client_id + client_secret). El secret nunca se

imprime: se inyecta como variable de entorno desde el gestor de secretos.

  1. Identidades reales — GET /v2.0/Users?count=200 y GET /v2.0/Groups?count=50

(SCIM 2.0). El tenant devuelve ~140 usuarios y 20 grupos reales: de ahí salen

userName, displayName, email e id SCIM de cada evento.

  1. Síntesis del evento — por cada iteración se arma un payload con forma de telemetría

SOC/IAM: event_type (p.ej. sso.login.success, mfa.verify.success,

fido2.authenticate, scim.group.member.added, risk.score.evaluated,

access.cert.reviewed), subject{} con la identidad real, application,

mfa_method, risk_level/score, ip, geo y occurred_at.

  1. Ingesta en n8n — POST al webhook https://n8n.example.com/webhook/isv-events.

Cada 200 dispara una ejecución del workflow ISV events sink:

Webhook ISV → Capture payload → Save to isv_events (ver captura).

Correrlo (100 eventos, secret inyectado, sin exponer el valor):

cd pike-web/janus
export PATH="/c/Program Files/nodejs:$PATH"
CID=<api-client-id> CSEC=<api-client-secret> node.exe isv-event-gen.mjs 100

Verificarlo — en la UI de n8n, /workflow/<workflow-id>/executions: la columna

muestra todas las ejecuciones Succeeded en modo webhook. En esta corrida: **303

ejecuciones, 100% success**. Cada una guarda el $json.body real capturado por el nodo

*Capture payload*.

Por qué "E2E real": el que las identidades salgan del tenant vivo (no de una lista

hardcodeada) hace que los labs sean creíbles — los mismos usuarios que ves en Verify

aparecen en el historial de eventos. El único trozo sintético es el tipo de evento,

porque el API client de este tenant no tiene scope sobre el Activity/Events API

(GET /v1.0/events → 403); con ese scope, el generador replicaría eventos históricos

reales en vez de simularlos.
