Respuesta adaptativa: contener un login anómalo de IBM Verify en segundos

> Estado: Blueprint ejecutable — workflow n8n importable en n8n-templates/adaptive-threat-response.workflow.json · NO activado en el tenant live (gate DRY_RUN=true).

> El escenario: si el Threat Detection de IBM Verify detecta un inicio de sesión anómalo (viaje imposible, IP sospechosa o fuerza bruta), no te limites a enviar un correo pasivo; con n8n degradas al usuario en WordPress a rol de solo lectura y le fuerzas un enrolamiento de Passkey FIDO2 para recuperar privilegios.

Para humanos

Recibir un correo de alerta cuando un atacante ya tiene una sesión abierta downstream no mitiga el impacto. La respuesta adaptativa conecta las señales de riesgo del IdP con contención activa y gradual antes de que ocurra movimiento lateral.

El flujo procesa las alertas diferenciando la severidad:

  • Riesgo Medio: no suspendemos la cuenta para evitar fricción innecesaria. En Verify no existe un endpoint directo de "forzar MFA"; en su lugar, aplicamos PATCH /v2.0/Groups/{step-up-required} agregando al usuario a un grupo SCIM asociado a una política de acceso que exige Passkey FIDO2 obligatoria. Se envía un email "¿fuiste tú?" y un nodo Wait retira al usuario del grupo tras 24 horas si no hay reincidencia.
  • Riesgo Alto: contención inmediata en dos frentes. Se inhabilita la cuenta en Verify (active:false) cortando la re-autenticación OIDC y se degrada de inmediato el usuario en WordPress a rol subscriber (POST /wp-json/wp/v2/users/{id}). El SOC recibe la telemetría (IP, país, score) y el flujo espera aprobación manual mediante un webhook (/reinstate).

> [!NOTE]

> La ruta de ingesta de eventos de riesgo (GET /v1.0/.../events) está POR VALIDAR, supeditada a cerrar el backlog #10 (API client read-only para telemetría).

Guard-rails (lo serio)

  • Falsos positivos y personas reales: la suspensión automática (active:false) solo se ejecuta con score ALTO y sobre cuentas no críticas. Desplegar en modo DRY_RUN para calibrar umbrales antes de activar escritura.
  • Allow-list para VIP / Break-Glass: administradores maestros y cuentas de emergencia break-glass quedan excluidos de acciones automáticas para prevenir auto-bloqueos.
  • Circuit breaker: límite estricto de suspensiones automáticas por hora (p. ej. máx. 5 suspensiones/hora) para mitigar ataques de denegación de servicio por spoofing.
  • Idempotencia: cursor temporal y deduplicación estricta por eventId para no procesar el mismo evento en múltiples ejecuciones.
  • Seguridad del token: cliente de API secundario de Verify con permisos mínimos (manageGroupMembers y actualización acotada); el Bearer token nunca se vuelca en logs ni mensajes.
  • Reversibilidad: la acción de cuarentena nunca elimina cuentas (DELETE), solo conmuta active:false y es 100% reversible mediante active:true y restauración del rol previo en WordPress.

   demoteWP = POST /wp-json/wp/v2/users/{id}{roles:["subscriber"]}

Artefacto

El flujo completo está empaquetado como workflow n8n importable listo para desplegar.

Cómo importarlo:

  1. En n8n, navega a Workflows → Import from File
  2. Selecciona adaptive-threat-response.workflow.json
  3. Configura las variables de entorno:
  • VERIFY_TENANT: URL base del tenant (p.ej. https://tenant.verify.ibm.com)
  • STEP_UP_GROUP_ID: ID del grupo SCIM vinculado a la política FIDO2
  • WP_SITE: URL del sitio WordPress downstream
  • SLACK_WEBHOOK: Webhook para alertas SOC
  1. Verifica que DRY_RUN=true en el nodo Guard Rails Config antes de activar
  2. Ejecuta en modo dry-run para calibrar umbrales de riesgo
  3. Una vez validado, cambia DRY_RUN=false y activa el workflow

Recordatorio: La ruta de ingesta de eventos (GET /v1.0/events) está pendiente de validar según backlog #10. Reemplazar el trigger Schedule por Webhook si el tenant soporta event streaming en tiempo real.
