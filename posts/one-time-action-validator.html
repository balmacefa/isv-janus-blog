One-Time Action Validator: re-verificar al humano en el clic destructivo

El SSO resuelve *quién entra*. Pero una sesión válida no significa que cada acción

dentro de ella deba ejecutarse a ciegas. Cuando un operador pulsa "Borrar asset" en

WordPress, ¿y si el sistema exigiera, *en ese instante*, una confirmación fuerte de que

es realmente él y que aprueba esa acción concreta — una sola vez?

Eso es el One-Time Action Validator (OTAV): step-up de autenticación por transacción

(no por login), con un token de un solo uso atado a la acción. IBM Verify valida al

humano; n8n orquesta; WordPress solo ejecuta si la validación pasa.

El flujo en vivo

*Click "Borrar" → se acuña un nonce single-use → passkey assertion → nonce consumido →

asset borrado una sola vez → un replay con el mismo token queda denegado.*

Ahora en vivo dentro de n8n (no es un mock)

El demo ya no corre en localhost: la UI la sirve el propio n8n y los webhooks

(/otav-mint, /otav-callback) son reales. El backend es un workflow n8n con el nonce

persistido en una Data Table, el enforce de un-solo-uso + TTL, y el **gate de riesgo

con Jev** corriendo dentro de n8n.

El step-up OIDC es un round-trip REAL contra IBM Verify. Al pulsar "Borrar", el

navegador se redirige de verdad al tenant con prompt=login y **Verify exige

re-autenticarse** antes de dejar continuar. Esta es la pantalla real que aparece:

Solo tras firmar en Verify, el tenant redirige al webhook /otav-callback con el code

y el state=nonce, n8n consume el nonce (una sola vez) y la accion procede. Esa pantalla

*es* la validacion extra: el humano re-verifica en el instante de la accion destructiva.

El problema

Una cuenta comprometida, un insider, o un simple clic accidental: con una sesión abierta,

las acciones destructivas (borrar, transferir, cambiar permisos) se ejecutan sin fricción.

El daño es inmediato e irreversible. Re-autenticar en el login no ayuda — el riesgo está

en la acción, horas después de entrar.

El patrón: step-up por transacción + token de un solo uso

WP: operador pulsa "Borrar asset Q4-report.pdf"
  → NO borra; pide a n8n un nonce {user, action:delete, assetId, exp:60s}
  → IBM Verify valida al HUMANO (step-up)  ──┐
  → n8n marca el nonce CONSUMIDO  ← aprobado  │
  → WP ejecuta el delete UNA sola vez
  2º clic / replay con el mismo nonce → DENEGADO (single-use)

El nonce es la clave: válido para *una* acción, *un* asset, *una* vez, y caduca en

segundos. Aunque alguien capture la aprobación, no la puede reusar.

Tres mecanismos de validación

1. 🟢 Re-auth OIDC (prompt=login, max_age=0)

Reutiliza el SSO OIDC que ya existe entre WordPress y Verify. En el clic, se redirige a

Verify forzando re-login; al volver autenticado, se acuña y consume el nonce. **Cero

enrolamiento extra** — funciona con lo que ya hay.

2. 🟢 FIDO2 / passkey assertion

El botón dispara un challenge WebAuthn (navigator.credentials.get) con el nonce como

desafío. Touch ID / Windows Hello / llave de seguridad resuelven en un gesto. Slick y

phishing-resistant.

3. 🟡 IBM Verify push (transacción en el móvil)

El IBM Verify Authenticator muestra *"¿Aprobar borrado de Q4-report.pdf?"* con el contexto

de la acción. Máximo wow y out-of-band. Requiere enrolar el authenticator + la API de

transacción MFA (nivel 2).

Jev decide CUÁNDO pedir step-up (gate de riesgo)

Pedir validación en *cada* clic mata la UX. Aquí entra Jev (juicios calibrados): evalúa

el riesgo de la acción y decide si amerita step-up. *Jev juzga, el código decide.*

AssetJev ¿requiere step-up?riesgoResultado
Q4-report.pdf (reporte financiero, producción, 1.2k descargas)0.960.99step-up obligatorio
borrador-temp.png (sandbox, 0 descargas)0.070.01pasa silencioso

El operador solo es interrumpido cuando de verdad importa. (Mismo motor de riesgo que el

caso *SoD Guardian* — se reusa.)

Corre dentro de n8n: el gate es un nodo HTTP del workflow que llama a

api.typesafe.ai/v1/systemone; cada mint devuelve needsStepup + riesgo juzgados por

Jev en produccion (la key vive en una credencial n8n, nunca en el codigo).

> Nota de captura: FIDO2 se automatiza con un *virtual authenticator* vía CDP

> (WebAuthn.addVirtualAuthenticator) para que la passkey complete sin Touch ID real —

> útil para grabar el demo headless (ver skill demo-media).

El código completo (otav-demo.mjs)

import { createServer } from "node:http";
const PORT = 7799;
const TENANT = "https://tenant.verify.ibm.com";
const WP_CLIENT = "isv-wp-oidc"; // el real vive en el OIDC app de WordPress
const nonces = new Map();        // nonce -> {action,assetId,used,exp}
let ASSET = { id: "a-q4", name: "Q4-report.pdf", exists: true };
const uid = () => "otav_" + Math.random().toString(36).slice(2, 10);
const json = (res, o) => { res.writeHead(200, {"content-type":"application/json"}); res.end(JSON.stringify(o)); };
const body = req => new Promise(r => { let d=""; req.on("data",c=>d+=c); req.on("end",()=>r(d?JSON.parse(d):{})); });

createServer(async (req, res) => {
  const u = new URL(req.url, "http://x");
  if (u.pathname === "/") { res.writeHead(200, {"content-type":"text/html"}); return res.end(PAGE); }

  // ① acuñar nonce single-use atado a la acción
  if (u.pathname === "/mint") {
    const b = await body(req); const n = uid();
    nonces.set(n, { ...b, used:false, exp: Date.now()+60000 });
    return json(res, { nonce:n });
  }
  // ② consumir (un solo uso; rechaza desconocido/ya-usado/expirado)
  if (u.pathname === "/consume") {
    const { nonce } = await body(req); const e = nonces.get(nonce);
    if (!e)            return json(res, { ok:false, reason:"desconocido" });
    if (e.used)        return json(res, { ok:false, reason:"ya-usado" });
    if (Date.now()>e.exp) return json(res, { ok:false, reason:"expirado" });
    e.used = true;     return json(res, { ok:true });
  }
  // ③ ejecutar la acción (solo si el nonce fue consumido)
  if (u.pathname === "/delete") {
    const { nonce } = await body(req); const e = nonces.get(nonce);
    if (!e || !e.used) return json(res, { ok:false });
    ASSET.exists = false; return json(res, { ok:true, name: ASSET.name });
  }
  // step-up 1: URL real de re-auth OIDC (prompt=login fuerza re-verificación)
  if (u.pathname === "/oidc-url") {
    const { nonce } = await body(req);
    const url = `${TENANT}/oidc/endpoint/default/authorize?client_id=${WP_CLIENT}`
      + `&response_type=code&scope=openid&prompt=login&max_age=0`
      + `&redirect_uri=http://localhost:${PORT}/oidc-callback&state=${nonce}`;
    return json(res, { url });
  }
  // step-up 3: push al móvil (mock nivel-2)
  if (u.pathname === "/push-approve") { await new Promise(r=>setTimeout(r,1600)); return json(res, { approved:true }); }
  if (u.pathname === "/reset") { ASSET.exists = true; return json(res, { ok:true }); }
  res.writeHead(404); res.end("nope");
}).listen(PORT, () => console.log("OTAV demo en http://localhost:" + PORT));
