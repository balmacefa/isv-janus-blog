Acceso privilegiado efímero (JIT): admin temporal en WordPress con auto-expiración en Verify

> Estado: Blueprint ejecutable — workflow n8n importable en n8n-templates/jit-privileged-access.workflow.json · NO activado en el tenant live (gate DRY_RUN=true).

> El escenario: mantener administradores permanentes en WordPress es una mala práctica que amplía la superficie de ataque. Cuando un desarrollador necesita resolver una urgencia técnica, solicita elevación temporal por chat y, tras la aprobación de su líder, n8n lo añade al grupo admin en IBM Verify y programa la revocación automática a los 30 minutos.

Para humanos

El acceso Just-in-Time (JIT) erradica las cuentas con privilegios permanentes (*standing privileges*). Los desarrolladores operan por defecto con el rol base developer. Cuando se requiere mantenimiento de infraestructura o configuración en WordPress:

  1. Solicitud ChatOps: El desarrollador envía /jit-request motivo="hotfix en wp-config" duracion=30m.
  2. Aprobación de cuatro ojos: El líder técnico recibe un mensaje interactivo en Slack/Telegram para aprobar o rechazar la solicitud.
  3. Escalamiento JIT en Verify: n8n añade al usuario como miembro del grupo admin vía SCIM. En el próximo refresh de token OIDC, WordPress mapea el claim de grupos y eleva la sesión a rol administrator.
  4. Auto-expiración programada: Transcurridos los 30 minutos, n8n ejecuta la revocación automática de membresía en Verify, devolviendo al usuario a su rol habitual y notificando la expiración.

Guard-rails (lo serio)

  • Escritura y elevación de privilegios: Operación sensible de alto riesgo; requiere webhook firmado (HMAC) y aprobación humana obligatoria (*principio de 4 ojos*).
  • Auto-expiración y reversibilidad: Toda concesión tiene un TTL estricto (30 min) y se revoca por diseño; si la sesión concluye antes, se puede revocar manualmente bajo demanda.
  • Idempotencia: Comprobación previa de pertenencia para no duplicar asignaciones y verificación de integridad para no remover jamás al último administrador del sistema.
  • Webhook firmado: Validación estricta de firma criptográfica para impedir spoofing o inyecciones de solicitudes no autorizadas.
  • Seguridad del token: Las credenciales de API (client_credentials) y el Bearer token de IBM Verify nunca se imprimen en logs de ejecución ni se envían en mensajes de notificación.

Artefacto

  • Descarga: workflow n8n importable
  • Cómo importarlo: n8n → Import from File → selecciona el .json. Crea las credenciales por nombre (IBM Verify - Client Credentials (SCIM), Telegram aprobador/auditoría) y define las variables de entorno VERIFY_TENANT, JIT_HMAC_SECRET, JIT_APPROVER_CHAT_ID, JIT_AUDIT_CHAT_ID. El JSON no contiene secretos.
  • Recordatorio: las escrituras (PATCH add/remove sobre /v2.0/Groups) van tras el gate DRY_RUN=true (nodo Config DRY_RUN); el workflow se entrega active: false.
