El problema de fondo: un catch-22

Queríamos que cualquier visitante disparara una aserción FIDO2 que **IBM Verify

verificara de verdad**. Chocamos con dos muros que, juntos, parecían imposibles:

¿Alcanza Verify?
¿Puede hacer WebAuthn del RP de Verify?
Navegador del visitante (IP residencial)✅ sí❌ no — WebAuthn ata el origin, y la página está en *nuestro* dominio, no en el del tenant
Nuestro servidor (n8n/cloud)❌ no (ver Muro 2)✅ sí — un autenticador por software firma lo que sea

Ninguno de los dos podía hacer las dos cosas. Resolverlo requirió atacar cada muro por

separado.

Muro 1 — Un autenticador WebAuthn por software que IBM Verify acepte

WebAuthn normalmente lo ejecuta un navegador con hardware (Touch ID / Windows Hello). Pero

el navegador ata el origin al Relying Party (RP). El RP FIDO2 del tenant solo acepta su

propio origin (https://tenant.verify.ibm.com), así que **ninguna página en otro dominio

puede hacer WebAuthn contra él. La salida: un autenticador por software** que fija el

origin él mismo y firma — no está atado a la política de origin del navegador.

La API FIDO2 de IBM Verify (lo que tardamos en mapear)

RP:  GET  /config/v2.0/factors/fido2/relyingparties           -> { id:<fido2-rp-id>, rpId, origins }
reg: POST /v2.0/factors/fido2/relyingparties/<fido2-rp-id>/attestation/options  (body: {userId})
     POST /v2.0/factors/fido2/relyingparties/<fido2-rp-id>/attestation/result
assert: POST .../assertion/options  (body: {userId})
        POST .../assertion/result

Gotchas que nos costaron sangre:

  • attestation/options exige userId (el id SCIM del usuario, no "me").
  • El body de attestation/result NO lleva userId (va atado al challenge/sesión). Mandarlo da CSIBN0005E: request body is invalid: userId.
  • El token server-side (client_credentials) da 403 en estos endpoints hasta que al API client le agregás el entitlement authnAnyUser ("Authenticate any user"). Ese fue el desbloqueo del token.
  • El userHandle de la aserción = el user.id que devolvió options (base64url).

Construir la attestation (registro) — CBOR a mano

El attestationObject es CBOR. Sin librerías, implementamos el subconjunto necesario:

// authData = rpIdHash(32) + flags(1) + signCount(4) + attestedCredentialData
// flags: 0x45 en registro (UP|UV|AT), 0x05 en aserción (UP|UV, sin AT)
// attestedCredentialData = aaguid(16, ceros) + credIdLen(2) + credId + COSEpublicKey
// COSE P-256 (CBOR map): {1:2(EC2), 3:-7(ES256), -1:1(P-256), -2:x(32), -3:y(32)}
// attestationObject (CBOR map): {fmt:"none", attStmt:{}, authData:<bytes>}
// clientDataJSON: {type:"webauthn.create", challenge:<b64url>, origin:<tenant origin>, crossOrigin:false}

Con fmt:"none" no hace falta firma de attestation (simplifica mucho). Resultado:

attestation/result devolvió 200 → passkey enrolada en el tenant. 🎉

Construir la aserción (login) — más simple, SIN CBOR

La aserción no necesita CBOR: authenticatorData son bytes planos y la firma es ECDSA

DER sobre authData ‖ sha256(clientDataJSON). En Node, crypto.createSign('SHA256')

sobre una clave EC ya devuelve DER (no hace falta convertir de P1363):

const authData = Buffer.concat([rpIdHash, Buffer.from([5,0,0,0,0])]);      // UP|UV, signCount 0
const cdj = Buffer.from(JSON.stringify({type:"webauthn.get", challenge, origin:"https://tenant.verify.ibm.com", crossOrigin:false}));
const signed = Buffer.concat([authData, crypto.createHash("sha256").update(cdj).digest()]);
const der = crypto.createSign("SHA256").update(signed).sign(PRIV);          // DER directo
const body = { type:"public-key", id:CREDID, rawId:CREDID, response:{ authenticatorData:b64u(authData), clientDataJSON:b64u(cdj), signature:b64u(der), userHandle:UH } };
// POST assertion/result -> 200 = IBM Verify VERIFICÓ la firma

assertion/result → 200. Verify verificó una aserción de nuestro autenticador por

software. Muro 1 cruzado. El origin lo pusimos nosotros (= el del tenant), así que la

clave no está atada a ningún navegador.

Muro 2 — La odisea de red (el contenedor no alcanzaba Verify)

Con el autenticador listo, lo movimos a un endpoint n8n público… y timeout. El

contenedor n8n (en un VPS cloud) no alcanzaba el tenant, aunque sí llegaba a

www.ibm.com y a otras APIs. Descartamos de a uno:

  • ¿DNS? El Code node de n8n tiene require('dns') bloqueado; no se puede forzar

IPv4 ahí. Pero www.ibm.com resolvía bien → no era DNS general.

  • ¿WAF de Cloudflare? No: el WAF es tráfico entrante (visitantes→n8n), no afecta la

salida del contenedor.

  • Diagnóstico con reachability real (desde el propio contenedor, via this.helpers.httpRequest):
api.typesafe.ai      -> HTTP 404  (control: egress funciona)
www.ibm.com          -> HTTP 200  (IBM alcanzable)
tenant.verify.ibm.com-> timeout   (el tenant NO)

Específico del host del tenant. Montamos un Cloudflare Worker como proxy (el contenedor

sí alcanza Cloudflare, y CF tiene red global)… y 520. El Worker corría (header

x-proxied-by presente), el cf-ray mostraba colo FRA (Frankfurt), y el body del 520

era "error code: 520" = la fetch de CF a Verify no obtuvo respuesta válida (conexión

caída).

El test decisivo: ¿es cloud o es región?

Forzamos un Durable Object con locationHint:"enam" (Norteamérica este) y le pedimos que

reportara su colo + probara Verify:

{ "doColo": "ORD", "verifyStatus": "HTTP 400" }

ORD = Chicago, EE.UU. → Verify RESPONDIÓ (400, no timeout). La bomba: **no era bloqueo de

cloud — era REGIONAL.** Europa (FRA / el VPS) no rutea al edge Akamai del tenant; EE.UU. sí.

El segundo truco: headers limpios

Con el DO en EE.UU., el /relay-diag (fetch limpia) daba 200… pero el proxy completo seguía

dando 520. Diferencia: el proxy reenviaba todos los headers (incluidos

cf-connecting-ip, x-forwarded-for que agrega CF). **La bot-defense de Akamai dropea la

conexión al ver headers de proxy/cloud. Fix: reenviar solo** authorization +

content-type (+ accept).

El Worker final (relay anclado en EE.UU. + headers limpios)

const TENANT = "https://tenant.verify.ibm.com";
export class Relay {              // Durable Object -> egress desde su región
  async fetch(req) {
    const target = req.headers.get("x-target");
    const h = new Headers();       // SOLO headers limpios (clave: no reenviar cf-*/x-forwarded-*)
    const a = req.headers.get("authorization"); if (a) h.set("authorization", a);
    const c = req.headers.get("content-type");   if (c) h.set("content-type", c);
    h.set("accept", "application/json");
    const up = await fetch(target, { method:req.method, headers:h, body:["GET","HEAD"].includes(req.method)?undefined:req.body, redirect:"manual" });
    const buf = await up.arrayBuffer();
    return new Response(buf, { status:up.status, headers:{ "content-type": up.headers.get("content-type")||"" } });
  }
}
export default {
  async fetch(req, env) {
    if ((req.headers.get("x-otav-proxy")||"") !== (env.PROXY_SECRET||"")) return new Response("forbidden",{status:403});
    const path = new URL(req.url).pathname.replace(/^\/verify/, "") || "/";
    const stub = env.RELAY.get(env.RELAY.idFromName("verify-relay"), { locationHint: "enam" });  // <- fija EE.UU.
    const h = new Headers(req.headers); h.set("x-target", TENANT + path); h.delete("x-otav-proxy"); h.delete("host");
    const body = ["GET","HEAD"].includes(req.method) ? undefined : await req.arrayBuffer();
    return await stub.fetch("https://relay.internal/", { method:req.method, headers:h, body });
  },
};

Apuntamos el Code node de n8n al Worker (https://<worker>.workers.dev/verify + header

x-otav-proxy), y… verifiedByVerify:true. Muro 2 cruzado. El camino final:

visitante → n8n (Europa) → CF Worker → Durable Object (ORD/EE.UU., headers limpios) → IBM Verify ✓

Cheat-sheet de gotchas (para que no sufras)

n8n Code node (sandbox):

  • fetch no existe → usá this.helpers.httpRequest({...}).
  • require('dns') (y otros módulos) bloqueados; crypto (node) sí funciona.
  • respondToWebhook: el status code va en options.responseCode, no top-level.
  • Rate-limit por IP: $getWorkflowStaticData('global') persiste entre ejecuciones; la IP real detrás de Cloudflare está en cf-connecting-ip.

Inyectar un secreto en n8n sin que aparezca en logs/historial: poné un placeholder

@@SEC@@ en el jsCode, hacé GET del workflow por la API de n8n, reemplazá el placeholder

con el secreto (leído de tu gestor) y PUT el workflow — el valor solo viaja server-side.

(Ojo: el PUT desactiva el workflow → reactivalo.)

Cloudflare Workers:

  • Un Worker corre en el colo cercano al cliente. Si ese colo no alcanza tu origen, usá

un Durable Object con locationHint para fijar la región del egress.

  • Body "error code: 520" = la fetch() del Worker no obtuvo respuesta válida del origen.
  • Al proxyear, no reenvíes cf-connecting-ip/x-forwarded-for si el origen tiene

bot-defense (Akamai): reenviá solo lo esencial.

  • Diagnóstico de colo: fetch('https://cloudflare.com/cdn-cgi/trace') → colo=XXX.

WebAuthn / IBM Verify:

  • El origin lo controla el autenticador por software (no estás atado al navegador).
  • fmt:"none" evita la firma de attestation.
  • crypto.createSign sobre clave EC devuelve firma DER (lista para assertion/result).
  • Entitlement authnAnyUser habilita los endpoints de factores para el token server-side.

Reproducir el lab

  1. Autenticador: portá el autenticador por software (CBOR/COSE/authData/DER) — Node nativo, sin deps. Registrá una credencial fija para un usuario demo (attestation/options→build→result).
  2. Token: agregá authnAnyUser al API client → el token client_credentials ya llama los endpoints FIDO2.
  3. Relay CF: deploy del Worker + Durable Object con locationHint en la región que SÍ alcanza tu tenant; reenviá headers limpios; protegé con un PROXY_SECRET.
  4. n8n: Code node que hace token→assertion/options→firma con la clave fija→assertion/result, apuntando al Worker. Inyectá el secreto con el truco del placeholder.
  5. UI: botón que llama al endpoint y, si verifiedByVerify, consume el nonce single-use.
